# Git 협업과 PR

## 사용 시점

브랜치·커밋·이슈·PR 작성 또는 리뷰에 사용합니다. Skill 선택 자체가 원격 게시·머지 권한은 아닙니다.

## 팀 규칙

| 항목 | 형식 |
| --- | --- |
| 브랜치 | `종류/#이슈번호-작업자 이름` (예: `feat/#1-Theo`) |
| 커밋 | `종류/#이슈번호: 커밋메시지` |
| 이슈 제목 | `종류: 작업할 내용` |
| PR 제목 | `종류/#이슈번호: 작업한 내용` |

작업에 맞는 종류를 사용합니다.

- `feat`: 기능, `fix`: 버그, `docs`: 문서, `style`: 포맷, `design`: UI 스타일
- `test`: 테스트 코드·테스트 리팩터링, `refactor`: 제품 코드 리팩터링
- `build`: 빌드 파일, `ci`: CI 설정, `perf`: 성능, `chore`: 기타 수정·빌드 업데이트
- `rename`: 파일·폴더 이름만 변경, `remove`: 삭제만 수행, `add`: 패키지·파일 추가

팀은 Git Flow를 참고하며, CodeRabbit의 1차 리뷰 후 **팀원 최소 2명의 Approve**를 받아 머지합니다.
커밋은 작업 의미가 드러나는 작은 단위로 자주 남깁니다.

### 리뷰어가 이해할 수 있는 PR

PR 설명의 독자는 해당 소스코드를 계속 관리할 팀원입니다. 작업 일지나 파일 목록 대신
문제와 설계 의도, 변경으로 달라지는 동작을 이해할 수 있게 씁니다.

| 순서 | 담을 내용 |
| --- | --- |
| 개요 | 어떤 문제가 있고 왜 바꾸는지. 관련 이슈가 있다면 설명 문장 안에 링크 연결 |
| 작업 내용 | 무엇을 어떻게 바꿨고 왜 선택했는지. 핵심 흐름·책임, 달라지는 동작·영향·남는 제약. 기대 효과는 사실과 구분 |
| 확인 사항 | 원래 체크리스트를 기본으로 포함하고 작성자가 확인한 항목을 체크. 해당하지 않는 항목은 이유를 짧게 표시 |
| 구현 화면 | UI 변경이 있을 때 해당 기기의 화면·GIF 첨부 |
| 리뷰 시 중점적으로 봐주셨으면 하는 부분이 있나요? | 집중해서 봐줬으면 하는 설계 판단과 구체적인 질문, 합의가 필요한 사항 |
| 덧붙일 말 | 변경을 이해하는 데 필요한 추가 맥락·이미 정해진 후속 작업. 없으면 생략 가능 |

문제와 의도를 먼저 설명하고 구체적인 변경과 영향, 리뷰어의 의견이 필요한 지점으로 이어갑니다.
이슈는 개요 문장 안에서 자연스럽게 연결하고, 효과와 남은 점은 작업 내용에 함께 설명합니다.

예를 들어 배치 병렬 처리를 도입했다면, 배치 병렬 처리가 무엇이고 왜 필요한지 설명한 뒤
동시 실행 수와 메모리 사용을 어떻게 제한하는지 연결해서 설명합니다. 해당하지 않는 기술 설명을 형식적으로 채우지 않습니다.

- **크기와 분리:** PR은 작게 유지하고 약 400줄을 넘으면 분리를 검토합니다.
  분리할 때는 데이터 모델·인터페이스 등 기반 PR을 먼저, 이를 사용하는 기능 PR을 다음에 구성합니다.
  각 PR이 독립적으로 이해·리뷰 가능하도록 의존 관계와 대상 브랜치를 명시합니다.
- **다이어그램:** 변경을 이해하는 지도로 쓸 수 있는 클래스·시퀀스·흐름도를 본문에 첨부합니다.
  핵심 구성 요소와 연결을 실제 변경에 맞춰 표시합니다. UI 변경 화면은 다이어그램과 별도로 첨부합니다.
- **검증 책임:** 작성자가 필요한 테스트와 검토를 마친 뒤 PR을 엽니다.
  본문의 기본 체크리스트로 작성자가 확인한 사항을 표시하되, 명령·실행 로그 전체를 나열하도록 요구하지 않습니다.
  리뷰어에게 다시 실행하거나 검증해 달라고 요청하지 않습니다.
  검증을 완료하지 못했다면 작성자의 남은 작업으로 다루고, 통과했다고 꾸미거나 리뷰어에게 넘기지 않습니다.
- **리뷰 전 공유:** 리뷰 전에 10–15분 동안 배경·다이어그램·설계 의도·불확실한 지점을 짧게 공유합니다.
  에이전트는 설명 자료를 준비할 수 있지만 팀의 일정·여유·역할·회의 가능 여부를 추정하거나
  공유가 이미 진행됐다고 표시하지 않습니다. 실제 일정·참석자와 진행 여부는 팀이 정합니다.

## 절차

1. `git status --short`와 현재 브랜치·diff를 확인하고 사용자 변경을 보존합니다.
2. 일반 작업은 최신 `develop`을 기준으로 분기합니다. 이슈 번호·작업자 이름은 요청과 이슈에서 확인합니다.
   기존 작업 브랜치를 이어가는 요청이라면 해당 브랜치를 사용합니다.
3. `#`가 있는 브랜치는 셸에서 전체 이름을 인용합니다.
   예: `git switch -c 'docs/#32-Devin'`. 이미 존재하는 브랜치를 덮어쓰지 않습니다.
4. 커밋 전 의도한 파일만 포함됐는지 확인하고 [verify-change](../verify-change/SKILL.md)에 따라 작성자 검증을 수행합니다.
5. PR의 전체 변경 규모와 의존 관계를 보고 작은 단위로 리뷰할 수 있는지 판단합니다.
   분리가 필요하면 기반·기능 순서를 정하고 각 PR의 변경이 섞이지 않게 합니다.
6. [PR 템플릿](../../../.github/PULL_REQUEST_TEMPLATE.md)의 원래 제목·이모지·순서를 유지합니다.
   각 섹션 바로 아래의 안내 주석에 따라 내용을 채웁니다. 상세 질문·조건별 안내·예시는 필요한 항목만 참고합니다.
   확인 사항의 기본 체크리스트를 유지하고 작성자가 직접 확인한 항목만 체크합니다.
   필수 설명과 조건부 항목을 구분하고, 해당하지 않는 설명을 채우거나 안내 질문·예시를 그대로 복사하지 않습니다.
   작업 내용에 다이어그램을 첨부하고 UI 변경 시 iPhone/Watch 화면도 추가합니다.
   작성한 PR에서는 해당하지 않는 화면 절과 전달할 내용이 없는 덧붙일 말 절을 생략할 수 있습니다.
7. 일반 작업은 `develop` 대상인지 확인합니다. 순서가 있는 PR은 앞선 PR과의 의존 관계에 맞춰 대상을 정합니다.
   리뷰 전 공유를 위한 설명 순서와 논의점을 준비하되, 일정 조율이나 타인에게 메시지 전송은 요청 범위를 따릅니다.

## 주의사항과 예외

- 참고 Git Flow 글의 모든 운영 선택을 팀의 새 필수 정책으로 확대하지 않습니다.
- 승인 수를 에이전트 리뷰나 CodeRabbit 리뷰로 대신 채우지 않습니다. 승인을 임의로 표시하지 않습니다.
- CI의 SwiftLint 자동 수정·커밋·push 로직은 로컬 작업 절차가 아닙니다.
- 사용자 요청 범위 없이 머지·force push·브랜치 삭제를 실행하지 않습니다.
  PR 게시도 현재 요청에서 허용된 범위인지 확인합니다.
- 결과가 좋아 보이도록 수치나 효과를 추정해서 쓰지 않습니다. 작성자 검증과 설계 리뷰의 책임을 혼동하지 않습니다.

## 결과 검증

브랜치·커밋·PR 제목의 형식, 이슈 연결, 대상 브랜치와 의존 관계를 확인합니다.
본문에 문제와 의도, 변경 내용과 영향, 리뷰 포인트와 다이어그램이 있고, 리뷰어에게 재검증을 맡기는 내용이 없는지 확인합니다.
리뷰 대기와 머지 완료를 구분하고, 로컬 브랜치만 생성했다면 원격 게시한 것처럼 보고하지 않습니다.
