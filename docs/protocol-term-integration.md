# 프로토콜 용어 연동

## 처리 흐름

1. `ProtocolAnalysisClient`가 외부 OmniParser 패키지로 문서를 읽습니다.
2. 타이머는 파싱한 본문에서 `ProtocolTimerExtractor`가 숫자·시간 단위를 찾아 추출합니다.
3. 용어는 R117 후보 생성·재정렬·선택을 거친 뒤 Foundation Models로 분류하는 구조입니다.
4. 분류 결과는 시약·재료, 샘플·분석 대상, 실험 용어, 단위로 검토 화면에 전달합니다.
5. 검토 후 저장한 용어는 실험 상세의 `speechContextualStrings`를 통해 녹음 시작 시
   `SFSpeechAudioBufferRecognitionRequest.contextualStrings`에 전달됩니다.

## 자동 타이머 판별

- 숫자에 붙은 시간·분·초와 영문 시간 단위를 초로 합산합니다. `1시간10분`, `5m30s`를
  지원하고 서로 다른 줄의 시간은 합치지 않습니다.
- `m/s`, `m/h`, `㎜/h`, 면적·빈도 단위는 지속시간으로 취급하지 않습니다.
- 자동 추출 타이머는 문서 안과 문서 사이에서 같은 초 값을 순서대로 한 번만 남깁니다.
  수동 추가 타이머와 이미 저장된 실험 데이터는 이 정리의 대상이 아닙니다.
- `10~20분`처럼 확정값이 아닌 범위는 양 끝을 독립 타이머로 자동 생성하지 않습니다.

## 현재 구현 범위

- Foundation Models 분류는 최대 25개씩 요청하며 각 요청마다 새 세션을 만듭니다.
  해당 배치의 용어가 출현한 원문 주변을 최대 1,200자까지 맥락으로 전달합니다.
- 응답은 요청한 원문 용어와 정확히 일치하고 중복 라벨이 없을 때만 채택합니다.
  모델이 생성한 새 용어·번역·표면 변경은 반영하지 않습니다.
- 기기·설정상 Foundation Models를 사용할 수 없거나 응답에서 라벨이 누락되면 단위 표기
  규칙으로 보완하고 나머지를 실험 용어에 보관합니다. 정확한 분류 완료라는 의미는 아닙니다.
  모델 준비 중·일시 요청 제한·생성 오류는 완료 배치를 보존한 뒤 재개 대상으로 남깁니다.
- 자동 추출 결과는 22자로 자르지 않습니다. 직접 입력의 기존 길이 검사는 유지합니다.
- 취소된 분류는 결과를 반환하지 않습니다. 분석 요청 식별자와 취소 상태가 오래된 결과를 막습니다.
- 문서 파싱에 성공했지만 용어 추출이 실패하면 본문·타이머는 유지하고 직접 입력 안내를 표시합니다.
- `R117TermExtractor`는 actor에서 후보 생성 → shortlist → 특징·teacher/F 계산 →
  seed42 head → alias·중첩 최종 선택을 실행하도록 연결했습니다.
- 공유 문맥 경로는 호출 actor에서 모델·토큰화를 준비한 뒤, 문서 original/teacher 인코딩과
  공유 last2 인코딩을 겹쳐 실행합니다. 모델별 window 누산과 정밀 100개 재검토는 유지합니다.
- 모델·자산은 `LabcordiOS/Resources/R117`에 포함하고 SwiftPM `Bundle.module`로 읽습니다.
- 원본 decoder의 가변 설정과 모델 호출은 공유 worker actor로 직렬화합니다.
  window·후보 반복 사이와 결과 반환 전 취소를 확인합니다.
- OSLog subsystem `com.labcord`, category `R117`에 추출 소요 시간을 기록합니다.
  모델 초기 로딩을 포함할 수 있으며 메모리·전사 개선 측정값은 아닙니다.

## 문서 영역과 용어 정리

R117의 입력 본문·모델 자산·최종 선택 규칙은 유지합니다. 앱은 문서 공유 문맥과 상위 100개
재검토를 사용하므로 후보별 문맥만 사용한 기존 점수와는 달라질 수 있습니다. 아래 공유 문맥
비교 결과와 적용 범위를 참고합니다. 문서 기반 호출은 선정한 용어의 Unicode scalar 위치를 파서 블록과 대조해 서로 다른 블록·표 셀·목록·반응식 경계를 넘는 후보를
정리합니다. 구조 정보를 잃은 텍스트만으로 경계를 추측하지 않도록 DocumentParseResult를
선별 API에 전달합니다. 정리 뒤 결과는 50개보다 적을 수 있습니다.

- 괄호 안 영문 별칭·화학식은 보존합니다. 괄호 밖 목록 구분자로 이어진 서로 다른 용어를
  분리하며 `1,2-`, `N,N-` 같은 화학명 위치 표기는 목록 쉼표로 처리하지 않습니다.
- 같은 원문 구절에서 긴 용어 내부의 불완전한 조각임이 확인되면 중첩을 정리합니다.
  모든 출현의 완전한 표기가 동일할 때만 명확한 복합 장비명으로 복원합니다.
- OCR·화학식을 통째로 제외하지 않습니다. 스캔 문서와 온전한 화학식도 지원합니다.
  이 정리는 용어의 의미적 정확성 전체를 보장하거나 모델 점수를 확률로 바꾸는 필터가 아닙니다.

## 백그라운드 분석과 중단 복구

`ProtocolAnalysisJobManager`가 화면과 독립적으로 작업을 소유합니다. View는 작업 ID별 상태를
구독하며 화면 수명 종료만으로 분석을 취소하지 않습니다. 명시적인 건너뛰기·등록 종료는 취소로
구분합니다. 새 요청과 실행 시도 식별자를 확인해 취소·재개 전의 늦은 결과를 차단합니다.
취소·일시중단 상태는 즉시 반영하고, 다음 분석·재개는 이전 파서·추론과 시스템 작업의
종료를 기다린 뒤 시작합니다. 대기 후에도 작업 ID·상태를 다시 확인해 재취소된 작업이
실행되지 않게 합니다. 내부 실패의 일시중단은 자기 Task의 종료를 기다리지 않습니다.

- 입력 사본, 파싱 블록과 출처, 선정 용어, 완료된 분류 배치를 iPhone 앱의 Application Support에
  원자적으로 저장합니다. 이는 작업 복구용 보관이며 기존 실험 SwiftData 모델을 바꾸지 않습니다.
- 보관 파일은 `completeUntilFirstUserAuthentication` 보호와 백업 제외를 적용합니다.
  원본 파일은 덮어쓰지 않습니다. 손상·알 수 없는 버전의 체크포인트도 자동 삭제하지 않습니다.
- 앱 전환 후 계속할 작업은 `BGContinuedProcessingTaskRequest`로 제출합니다. 허용된 식별자는
  `$(PRODUCT_BUNDLE_IDENTIFIER).analysis.*`로 본앱과 QA 앱을 구분합니다. 등록은 ID별 한 번만
  수행하고 대기·실행·완료·만료를 처리합니다. 시스템 진행은 실제 완료 단계와 처리 수를 반영합니다.
  QA 배포 사본에서 번들 ID를 변경할 때도 허용 식별자를 실제 번들 ID에 맞춰 함께 변경해야 합니다.
- 현재 CPU 모델 경로에 GPU entitlement를 임의로 추가하지 않습니다. 시스템이 실행을 거부하면
  앱을 연 상태에서 처리하고, 백그라운드로 이동할 때 저장된 단계부터 재개 가능한 상태로 남깁니다.
- Simulator는 실제 백그라운드 스케줄링을 지원하지 않아 같은 중단·복구 경로를 사용합니다.
  앱 강제 종료 시 계속 실행한다고 약속하지 않습니다. 다음 등록 화면에서 저장한 작업을 복원하고
  `다시 시도`로 마지막 완료 단계 이후부터 이어갑니다. 시스템 UI 취소를 자동 재실행하지 않습니다.
- 타이머 범위·상한·하한·근삿값은 고정값으로 확정하지 않습니다. 검토 안내에서 원문 확인을
  요청하고 기존 타이머 추가·편집 기능으로 사용자가 결정합니다.

공식 기준은 [Apple 장시간 작업 문서](https://developer.apple.com/documentation/backgroundtasks/performing-long-running-tasks-on-ios-and-ipados)와
[Foundation Models 백그라운드 제한 안내](https://developer.apple.com/forums/thread/793787)를 확인합니다.


### 문서 기반 표기 정리와 단위 보충

선정된 용어는 파서 블록의 원문과 대조합니다. 불완전한 괄호나 숫자가 잘린 `%` 농도는
같은 블록 안의 모든 출현에서 완성 표기가 하나로 일치할 때만 복원합니다. 서로 다른
완성형·농도가 있으면 추측하지 않습니다. 정상 `85% 인산`, `70%에탄올`, `%R.H.`,
`수득률(%)`는 보존하고 괄호·대괄호·중괄호 안의 쉼표는 목록으로 나누지 않습니다.

측정 단위가 R117의 최종 상위 50개에 없더라도, 분류 완료 뒤 본문에 실제로 적힌 단위를
별도로 보충합니다. `mL`, `g/mol`, `m/s`, `W/m²`, `%R.H.` 등을 지원하며 수치와 단위를
분리합니다. 원문에 없는 지수나 OCR 오류를 추정해 만들지 않습니다. 단위 중복 키는
호환 문자·micro 문자·공백을 정리하되 `mm`과 `mM`의 대소문자는 구분합니다.
단독 `h`, `min`, `s`는 이 보충 경로에서 제외하고 시간 추출은 기존 타이머 경로가 맡습니다.
`m`은 분과 미터가 겹치므로 명시적인 길이·높이·거리 맥락과 단위 헤더에서만 미터로
보충합니다. 이 맥락은 타이머 오인·시간 범위 검토 경고를 제외할 때도 사용합니다.

단독 알파벳·접두사가 붙은 기호는 수치·표 머리글·단위 설명을 함께 확인합니다.
화학식의 말단, 문서 번호, 농도 변수, OCR 수식을 측정 단위로 승격하지 않습니다.
전도도 문서의 `uS/cm`, `mS/m`, `µS/cm`, `mho(s)/cm` 같은 실제 표기도 지원합니다.
기상 문서에서 누락됐던 `hPa`와 전도도 문서의 소문자 `ohm`·`ohms`도 보충합니다.
`ohm`·`ohms`·`Ω`는 같은 비교 키를 사용하고, `mho`·`mhos`는 같은 prefix 안에서만
묶어 처음 나온 표기를 유지합니다. 단위명과 기호의 기준은
[NIST의 ohm 안내](https://www.nist.gov/pml/owm/si-units-electric-current)와
[BIPM SI Brochure](https://www.bipm.org/en/publications/si-brochure)를 참고합니다.
전기 단위 `Ω`, `µF`, `mH`와 `ms`·`µs`·`ns`도 보충하며, 밀리초 이하를 분·초 타이머로
오인하지 않습니다. 숫자가 붙은 bare `F`·`H`는 전기 측정 문맥을 확인해 `F7`·`0H` 같은
실제 PDF의 OCR 조각과 구분합니다. 면적·부피의 `m2`·`m3`, 명시적인 지수는 보존합니다.

분류가 끝난 뒤 단위로 오분류한 전하 조각, 명시된 측정 변수, 문서 식별자 조각은 원문 근거가
있을 때 실험 용어로 옮기고 검토 안내를 표시합니다. `EC`·`tEC`는 같은 원문의 동일 수치
`°C`·`t°C` 표기와 대조되는 경우에만 옮깁니다. 근거가 부족하면 분류를 유지하고 확인을
요청하며 원문에 없는 단위로 변환하지 않습니다. 규칙에 없는 단위명을 일괄 제거하지 않아
`siemens`·`millisiemens` 같은 실제 단위명과 나머지 용어·순서를 보존합니다.

검토 화면과 자동 보충은 같은 비교 키를 사용합니다. `mM`과 `mm`, `mPa`와 `MPa`는
구분하고 `ul`·`µL`·`㎕`, `ml`·`mL`, `uS/cm`·`µS/cm`는 같은 표기로 비교합니다.
중복을 묶은 뒤에는 처음 나온 원문 표기를 보여 줍니다. 리터 표기의 변환은 단위 성분
경계에서만 수행해 `mol`·`nmol`의 철자를 바꾸지 않습니다. 수동 입력에서도 같은 규칙으로
서로 다른 SI 배율은 허용하고 같은 단위의 반복 추가는 막습니다.

R117의 최대 50개 선정 규칙은 유지하고 단위만 별도로 보충하므로 전체 표시 용어 수는
50개를 넘을 수 있습니다. 중간 분류 체크포인트에는 기존 선정 용어만 저장하고, 완료 결과에
보충 단위를 합칩니다. 이 구분으로 완료된 후보 prefix를 검사하는 중단·재개 계약을 유지합니다.


### Foundation Models 분류 응답

분류 입력의 실제 용어를 동적 스키마의 고정 속성 이름으로 두고 모델은 분류 값만 생성합니다.
응답 배열의 위치를 용어에 연결하지 않으며, 허용되지 않은 키·중복 키·알 수 없는 분류를
검사합니다. 누락된 라벨은 기존 보완 안내로 이어집니다. 선택된 용어, 원문 문맥, 네 분류,
25개 배치와 완료 prefix 체크포인트는 유지합니다.

같은 Simulator의 아스피린 38개 용어 비교에서 키 기반 응답은 기존 문자열 응답보다
적은 출력 토큰을 사용했습니다. 앱 경로의 warm 실행은 7.49초, 완료된 25개 이후 13개만
재개한 실행은 2.68초였고 저장된 분류와 일치했습니다. 최초 호출은 더 오래 걸릴 수 있으며
다른 문서·OS에서 같은 분류나 시간이 보장된다는 뜻은 아닙니다. 개수만 제한한 분류 배열은
용어 연결·분류 오류가 확인돼 사용하지 않습니다.

## 분석 진행 표시와 결과 이동

- 업로드·분석 중·완료 화면은 현재 상태에 맞는 하나만 구성해 숨은 이전 버튼이 접근성 탐색에
  중복 노출되지 않도록 합니다.
- 파서가 전달한 파일 확인·본문 읽기·OCR 단계를 표시합니다. 처리 중인 문서 번호·파일명과
  전체 경과 시간을 함께 보여주며, 문서 번호는 선택 목록에서의 위치입니다.
- 용어 추출 모델 준비 → 후보 생성 → 검토 모델 준비 → 후보 개수·문맥 처리 수 → 분류 처리 수 →
  결과 정리를 실제 작업 콜백으로 전달합니다. 준비 단계는 캐시가 없을 때만 표시합니다.

## 재시도·녹음 화면·실험 중단

- 본문 파싱은 성공했지만 용어 추출에 실패한 입력도 재시도할 수 있습니다. 재시도 시 성공한
  본문을 재사용하며, 파싱하지 못한 파일과 용어만 추출하지 못한 파일을 구분해 안내합니다.

  초기화·취소된 분석의 늦은 응답은 결과에 반영하지 않습니다.

점수·선정 순서 변경을 유발하지 않습니다.

실제 문서 진단에서는 입력 SHA-256, 파서가 반환한 본문, 후보 수, 최종 선정 시점의 별칭 보정과
중첩 감점을 함께 기록합니다. 초기 모델 준비와 추론 시간을 구분하고 Simulator 측정치를
실기기 성능으로 해석하지 않습니다. 점수는 선정 순위를 위한 값이며 확률이나 신뢰도가 아닙니다.

### 후보별 문맥 경로의 출력 보존 성능 개선

아래는 문서 공유 문맥 도입 전의 비교입니다. 기존 후보별 문맥 경로는
`R117Ranker.scoresConcurrently`에서 공식 Core ML async prediction을 모델당 최대
두 개씩 실행합니다. 후보 문맥 모델은 활성 CPU 수와 실제 입력 수에 따라 1~4개를 준비해
후보 단계에서 최대 여덟 개를 실행합니다. 짧은 입력은 필요한 모델만 로드하고 이후 재사용합니다.
모델 캐시를 준비하고 나머지 점수를 계산하는 코드는 호출한 추출 actor에
남깁니다. 동기 점수 경로는 대조용으로 유지합니다. 동시에 실행하는 것은 공식 async API이며,
같은 모델에 동기 prediction을 여러 스레드에서 호출하지 않습니다.

원본·teacher 문서 인코더는 같은 토큰화를 공유하고 두 모델을 함께 처리합니다. 각 모델의
512-token window와 stride 448을 유지하며 완료된 chunk를 원래 순서로 수거해 Float32
누산 후 Double 평균을 계산합니다. 두 문서 인코더가 끝난 뒤 후보 문맥 추론을 시작합니다.
취소 후 새 분석은 이전 추론의 종료를 기다리므로 같은 앱 작업에서 상한을 넘겨 겹치지 않습니다.

`R117Last2Plan`은 ±160 Unicode scalar 문맥과 510 토큰 제한, BOS/EOS와 후보별 pooling
위치를 보존합니다. 토큰 ID 배열이 완전히 같을 때만 한 번 추론하고 원래 후보 인덱스에
특징을 돌려줍니다. 서로 비슷한 문맥을 같은 입력으로 취급하지 않습니다. 각 그룹의 전체
hidden 출력을 계속 캐시하지 않고 필요한 후보 특징만 남깁니다.

문서의 token 좌표가 두 경계 모두 비감소 순서이면 겹치는 구간만 이진 탐색합니다.
정렬이 맞지 않으면 기존 전체 순회를 사용합니다. 반복·zero-width 좌표와 부분 겹침을
포함해 원래 가중치·누산 순서를 유지합니다. 실제 2,762-token 문서의 두 인코더에서
2,000개 후보의 상대 특징은 기존 비트와 같았고 Debug 1회에서 해당 단계가 각각
2.84→0.75초, 2.80→0.89초였습니다. 문서 전체 시간이 이만큼 보장된다는 뜻은 아닙니다.

진행 수는 부모 작업이 수거한 실제 완료 후보 수입니다. 추론 완료 순서와 결과 배열 순서를
분리하고 취소 전후를 검사합니다. 문서 피처의 scalar 배열·고정 정규식을 재사용하며,
Core ML 배열은 실제 stride를 따라 버퍼로 읽고 써서 원소별 NSNumber 변환을 줄입니다.
모델 자산, seed42, 구성 점수·가중치와 최종 선정 규칙은 유지합니다.

2026-11-03 iPhone 17 / iOS 27 Simulator Debug의 고정된 기상측기 2,000개 후보에서,
기존 후보별 문맥 계산 226.999초와 한 모델의 개선 경로 87.404초를 비교했습니다.
네 모델 경로는 별도 실행에서 36.519초였으며 같은 원본 특징과 비교했습니다.
2,000×384 Float의 비트가 모두 일치했고 원본 특징 바이너리 SHA-256은
`eb58440adb52c36b7674ccf99dd075ba1e4e662a9b2786b0438c132df530d26d`입니다.
이는 문서 전체 시간이나 실기기 성능이 아닙니다. **문서 입력부터 완료까지 15초 목표는
아직 달성하지 못했습니다.** 당시 공유 문맥 실험은 선정 결과가 달라져 반영하지 않았습니다.
이후 사용자 승인과 품질 비교를 거쳐 적용한 공유·재검토 경로는 아래에 구분해 기록합니다.

공식 API 기준은 [Core ML async prediction 안내](https://developer.apple.com/videos/play/wwdc2023/10049/)와
[MLMultiArray 버퍼·stride 안내](https://developer.apple.com/documentation/coreml/mlmultiarray/withunsafemutablebufferpointer(oftype:_:))를 참고합니다.

shortlist가 같았습니다. 초기화와 warm 실행을 구분해 기록했으며 속도 이득은 문서마다 다릅니다.
모델 수 5~6개와 OCR 언어 설정도 비교했지만 CPU 비용·본문 변화와 작은 시간 차이를 고려해
기본 최대 네 모델·자동 한영 OCR을 유지했습니다.

다음 분류 배치의 session을 첫 배치 실행 전에 `prewarm(promptPrefix:)`로 준비하는 실험도
분류 라벨은 같았지만 전체 시간의 일관된 감소가 없어 반영하지 않았습니다. 첫 baseline은
9.77초, warm baseline은 7.34초, 두 prewarm 실행은 7.65·7.83초였습니다. 예열 비용과 실제
대기 구간을 포함해 비교했으며 최초 자산 로드 차이를 개선 효과로 해석하지 않습니다.
API의 사용 시점과 백그라운드 제한은
[Apple prewarm 문서](https://developer.apple.com/documentation/foundationmodels/languagemodelsession/prewarm(promptprefix:))를 참고합니다.

경로는 내부 비교용으로 남기며 화면 설정은 추가하지 않습니다.

- `teacher_last2`는 문서를 510개 본문 토큰과 BOS/EOS로 나누고 stride 448로 처리합니다.
  같은 모델의 공식 async prediction을 최대 두 개씩 실행하며, 완료 순서와 무관하게 원래
  chunk 순서로 수거합니다. 겹친 토큰은 Float32 평균 후 후보 구간의 토큰을 같은 가중치로
  pooling합니다. 원본·teacher 문서 인코더의 기존 512-token 입력은 바꾸지 않습니다.
- 공유 점수 상위 100개는 기존 ±160 Unicode scalar·510-token 후보별 문맥으로 다시 추론합니다.
  동점은 원래 후보 인덱스를 따릅니다. 100개 이하의 입력은 처음부터 기존 후보별 경로로 처리합니다.
- 해당 인덱스의 last2 logit만 교체하고 **전체 후보 풀**의 정규화·점수 결합을 다시 계산합니다.
  다른 구성 점수와 head 출력은 재사용합니다. 모델 가중치·seed42·최대 2,000개 shortlist와
  alias·중첩 기반 최종 최대 50개 선택 규칙은 유지하지만 문맥·점수가 동일하다는 뜻은 아닙니다.
- 진행 수는 공유 평가를 마친 뒤 정밀 재검토 대상 수를 제외한 값에서 시작해 실제 재검토
  완료 수만 더합니다. 예를 들어 2,000개 입력이면 1,900→2,000입니다. 가상 시간·백분율은
  만들지 않습니다. 취소 후에는 진행 중인 추론 작업을 수거하고 종료한 다음 재개합니다.
- 이미 선정한 용어와 완료된 분류 배치는 기존 체크포인트를 그대로 사용합니다. 저장 형식이나
  실험 데이터 마이그레이션은 추가하지 않았고, 새로 선정하는 문서부터 이 경로를 사용합니다.

#### 품질 비교 범위

동일한 실제 PDF 본문·2,000개 후보·캐시를 사용해 후보별, 순수 공유, 공유 후 100개·200개

100개와 200개 재검토는 모두 네 문서의 기존 최종 선택 인덱스 50개와 정리 후 용어 **집합**을

대조한 수동 점검 목록이며 gold 정답·정확도 평가가 아닙니다. 이 네 입력의 집합 일치는 다른
문서·모든 모델 점수·용어 순서의 동일성을 보장하지 않습니다. 비용이 적은 100개를 적용했습니다.

포함한 전체 시간이나 실기기 성능으로 해석하지 않습니다. 초기 모델 로딩은 별도 기록했습니다.

`prewarm()`한 뒤 그 session으로 응답하는 경로도 비교했습니다. 양쪽에 같은 1초 선행 구간을

| 기상측기 | 11.80초 | 12.12초 |

반대였고, 캐시를 제거한 cold 대조가 아니므로 첫 입력의 차이를 일반적인 예열 효과로
해석하지 않습니다. 1초 대기는 진단에만 사용했으며 앱에 추가하지 않았습니다.

선정 동안 같은 session을 보유한 다음 분류에 사용했습니다. 인위적인 대기 없이 비예열→
예열→예열→비예열 순서로 실제 파싱·선정 API와 동일 분류를 계측한 경로를 실행했습니다.

- `usedFallback`은 모델 사용 불가·누락/무효 라벨·단위 재검토로 구분합니다. EC/tEC의 flag 설정과
  실제 glossary 이동, seed에서 물려받은 true도 구분합니다. 생성 오류는 기존 throw→pause를
  유지하고 fallback 성공으로 전환하지 않습니다. 정상 단위 추가도 모델 실패로 세지 않습니다.
- 일반 로그는 원문·용어·응답·파일 경로를 제외합니다. 해시도 익명화 보장이 없으므로 보호하며,
  요청 hash·첨부 작성 등 진단 자체의 비용을 별도로 기록해 전체 시간에서 숨기지 않습니다.

[Apple 성능 계측 안내](https://developer.apple.com/documentation/foundationmodels/analyzing-the-runtime-performance-of-your-foundation-models-app)의
Model Loading·Total/Response Duration·TTFT는 현재 Simulator에서 트랙 제공 여부를 확인한
경우에만 보조 관측합니다. 미지원이면 SDK 내부는 미관측으로 남기며 실기기를 요구하지 않습니다.
stream 첫 snapshot을 TTFT나 완성 라벨로 취급하지 않고, streaming 도입도 이번 최소 계측과
분리합니다. 동일 입력의 계측 off/on을 네 문서 각 세 번 교차 비교한 뒤 재개·취소·저장 실패를
검증하는 순서입니다. 입력·결과·진행 prefix·오류와 기록 부가 비용을 함께 봅니다.
